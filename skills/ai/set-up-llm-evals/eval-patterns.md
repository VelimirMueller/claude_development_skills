# Eval Patterns

Reference for [set-up-llm-evals](./SKILL.md). Code: [eval-code.md](./eval-code.md).

## Rule: The harness is a small in-repo runner on the production seam
**Why:** An eval is only as good as its resemblance to production. A harness that builds its own prompts and calls the SDK directly measures a different system than the one users get. Going through the seam means the same prompt files, the same schema validation, the same model config, the same redaction, and the same spans. The runner itself is about 100 lines; a dependency for that is more to learn and upgrade than the code it replaces.
**How to apply:** `evals/lib/run.ts` takes a `subject` function (the production use case, for example `summarizeTicket`) and the dataset. It runs checks, optionally a judge, writes JSONL, returns a summary. Datasets are files in the repo, reviewed like code.
**Tool choice, with reasons:**
- **In-repo harness (default, TypeScript):** one language, no vendor, runs in the existing test runner, the dataset and results are plain files.
- **Inspect AI (`inspect-ai`, MIT, UK AI Security Institute):** the pick for Python repos and for agentic evals with sandboxed tools; datasets, solvers and scorers compose, `inspect view` shows logs, `mockllm/model` makes the harness testable offline. Verified here: a task with `includes()` ran under the mock model and a log reader computed a gate.
- **promptfoo (MIT):** good when a non-programmer edits a YAML test matrix or you want its red-team generators. OpenAI agreed to acquire it in March 2026 and said it stays open source; for a neutral stack keep the config portable and do not make it the only copy of the dataset.
- **Braintrust and similar hosted tools:** pick them for team dashboards and online scoring of production traffic, not for the gate. Keep the golden set in the repo.
**Anti-example:** A Jupyter notebook that calls the API with prompts pasted from the code, run by hand before releases.

## Rule: Golden datasets live in the repo and grow from failures
**Why:** A dataset in a shared drive drifts from the code and nobody reviews changes to it. A dataset in git is versioned with the prompt it tests, and a PR that changes either shows both.
**How to apply:** JSONL under `evals/datasets/`, one case per line. Two tiers:
- `*-gate`: 20 to 30 frozen cases checked by deterministic assertions only. Fast, cheap, run on every relevant PR. Freeze it: edit a gate case only with a reason in the commit message, otherwise the baseline means nothing.
- `*-full`: 100 or more cases, judged, run nightly and on prompt, model or config changes.
Sources, in order of value: production failures (every bug becomes a case, with the input redacted), real inputs sampled and redacted, hand-written edge cases (empty input, very long input, other languages, injection attempts, unanswerable questions), synthetic cases generated by a model and then reviewed by a human. Label each case with a `source`. Start with 30; 30 reviewed cases beat 1,000 unreviewed ones.
**Anti-example:** Generating 500 cases with a model and never reading them: the dataset inherits the model's blind spots and you cannot tell.
**When to deviate:** Safety-critical features: grow the set before the feature ships, and add a sampled human review of production output.

## Rule: Deterministic checks first, a judge only for what they cannot express
**Why:** A program check is free, instant, exact and reproducible. A judge costs money, takes time, and has its own error rate. Use the cheap instrument wherever it works, and keep the judge for the properties a program cannot decide (is the summary faithful, is the tone right).
**How to apply:** Order per case: (1) schema validity (the seam already enforces it); (2) `must_contain`, `must_not_contain`, `must_match`; (3) task-specific checks (cited ids exist in the retrieved set, a refusal text appears for unanswerable inputs, no PII in output, length bounds); (4) the judge, only when 1 to 3 pass. A case that fails a deterministic check never reaches the judge, so a broken output does not cost a judge call.
**Anti-example:** Asking a judge "does the answer contain the order number?"

## Rule: A judge gets a rubric, a binary verdict and a calibration
**Why:** "Rate this 1 to 10" gives noise: scores drift between runs and between judge versions. A short list of binary criteria is stable and debuggable, and a human can say which criterion a failure broke. A judge you never compared with people is an opinion.
**How to apply:** `prompts/eval-judge.md` holds the rubric: three to five yes/no criteria, `pass` only if all hold, a one-sentence reason naming the first failed criterion. Treat input and output as data inside delimiters (the judge reads untrusted text too). Use a `balanced` or `quality` tier for the judge; a weaker judge than the subject is a common source of false passes. Calibrate: have a person label 30 to 50 real outputs pass/fail, run the judge on them, compute agreement and Cohen's kappa. Under 0.6, revise the rubric and recalibrate. Keep the labels in `evals/datasets/labels-<task>.jsonl` and rerun the calibration when the judge model or the rubric changes. For pairwise comparisons, randomize the order of the two answers: judges favour the first position.
**When to deviate:** A task with a verifiable answer (extraction, classification): skip the judge, compare to the label.

## Rule: Gate on a small deterministic set in CI; judge on a schedule
**Why:** A gate that takes 20 minutes and flakes gets disabled. A gate that never runs misses the regression. The split gives a fast, stable PR signal and a deeper nightly one.
**How to apply:** `eval-gate` runs the `*-gate` set with deterministic checks on PRs that touch `prompts/`, `config/llm.models.json`, `src/platform/llm/` or the feature. It fails on an absolute floor (`minPassRate`) **and** on a drop against the last recorded run (`maxDropVsBaseline`): the floor stops a bad launch, the drop stops slow decay. `eval-full --judge` runs nightly and on release branches and records to history. Model output varies between runs; run borderline cases several times and gate on the pass rate, not one sample. Some current reasoning models ignore or reject `temperature` and `top_p`; check the model card before relying on sampling settings to pin variance.
**Anti-example:** A threshold of 1.0 on a judged set: the first noisy run trains the team to ignore the gate.

## Rule: Every run has a budget and stops at it
**Why:** An eval loops over many cases, each with a model call and maybe a judge call. A dataset that doubles, a prompt that grows or a retry storm turns a nightly job into a surprise invoice.
**How to apply:** `thresholds.json` carries `budgetUsd` per dataset; the runner sums the cost the seam returns (subject and judge) and throws before the next case once the budget is reached. Estimate first: cases times average cost from the previous run. For large offline runs use the Batch API (50% cheaper, results within 24 hours), never for the PR gate. Cost per case is part of the result: a prompt change that doubles it is a regression even when quality holds.

## Rule: Track results over time, with what produced them
**Why:** A pass rate is meaningless without the prompt version, the model, and the dataset it came from. When quality drops in March you need to find the April change that fixed it, or the February one that broke it.
**How to apply:** `evals/history.jsonl` gets one line per recorded run: timestamp, dataset, pass rate, total, cost, git SHA, and the model id per tier. Per-case results go to `evals/results/` (gitignored, kept as a CI artifact). Prompt versions are on every span and in the repo history. A model upgrade is: change `config/llm.models.json`, run `eval-full`, compare with history, merge or revert.

## Rule: Evals run on the real model, unit tests on the fake
**Why:** The fake adapter proves your code handles responses. Only the real model proves the prompt works.
**How to apply:** Unit tests (`tests/evals.test.ts`) use the fake adapter and run on every commit. `evals/gate.ts` uses the real adapter, so it needs a key and costs money, which is why it is path-filtered and budgeted.

## When to deviate

- **A feature with no ground truth and low stakes** (a tone rewriter): skip the golden set, keep a handful of smoke inputs and watch production feedback.
- **Early prototype:** 10 hand-picked cases and the deterministic checks are enough; add the judge when the prototype becomes a feature.
- **Online evaluation of live traffic** (sampling production outputs through a judge): worth it once volume exists; a hosted tool is the practical route. It adds to, never replaces, the offline gate.
